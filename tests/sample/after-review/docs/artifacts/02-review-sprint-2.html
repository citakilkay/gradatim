Review

Shelf, after sprint 2

The shelves and the offline app shell work as planned, but adding a book is blocked with the network off, so M3 is marked delivered without meeting its Done when. The rest are small optional fixes, best made before M4 to M8 build on the home page and the store.

Made 2026-11-13 Sprints 1 and 2 Items 9

The top recommendation

1 · strong

Let a reader add a book with the network off. It's the MVP's main promise, the code, UI and features reviews all found it on their own, and it takes a quarter of a day. See item 1.

The recommendations

1

Let a reader add a book with the network off, and test it offline

strong

The problem
The Add button on /add is off whenever the browser is offline (src/routes/add/+page.svelte:48, disabled={saving || !$online}), and no message says why. So M3's Done when, "a book added with the network off shows on its shelf by its ISBN" (docs/MVP.md:29), doesn't hold, and neither does D4, "adding a book never blocks". It got through because BOK-3's criterion 1 left out "with the network off", and e2e/add-book.test.ts:3-15 only adds a book online. The UI review confirmed it: Add is greyed out at phone width (Pixel 7) and at 1280 wide with the network off.
The change
Take !$online out of the button's condition, since addBook only writes to IndexedDB (src/lib/books.ts:15-40). Add a Playwright case that waits for the service worker, goes offline, adds an ISBN through /add, and finds it on its shelf at both widths.
What it wins
M3 and the MVP's core offline promise really hold, and M4's lookup queue gets books added offline to work on.

2

Ask the browser to keep Shelf's data

optional

The problem
Until P1.3 syncs, IndexedDB holds the only copy of a reader's shelves. Nothing asks the browser to keep it: no persist appears in src or static. So the browser can evict the data when storage runs low, or after Safari's inactivity limit, without the reader clearing anything. docs/MVP.md accepts only the loss that comes from clearing the browser.
The change
Call navigator.storage.persist() once on the first open, beside ensureStartingShelves in src/routes/+layout.svelte:9-11, and add a unit test with the API stubbed.
What it wins
A reader's shelves are much less likely to vanish silently before sync exists.
The size
About 0.25 dev-days

3

Refuse a book whose shelf doesn't exist

optional

The problem
addBook saves any shelfId it gets, without checking that a live shelf has it (src/lib/books.ts:18-24, shelf?.name ?? ''). On /add, shelfId starts as '', and Add stays enabled while it's empty (src/routes/add/+page.svelte:10,16,22). A shelf deleted in another tab hits the same gap. The book that results shows on no shelf, and still blocks its ISBN with "That book is already on ." (an empty shelf name).
The change
Inside the transaction, refuse with reason: 'no-shelf' when the shelf is missing or deleted, and keep Add off until a shelf is picked.
What it wins
No orphan books, which nothing shows and nothing can add again.
The size
About 0.25 dev-days

4

Say something on an empty shelf

optional

The problem
A shelf with no books shows a blank box with no text (src/routes/+page.svelte:91-95, :164-169). On a first open, a new reader sees three empty boxes at /, at phone and desktop widths, with no hint about how to add a book.
The change
When a shelf has no books, show "No books yet" with a link to /add that picks this shelf.
What it wins
The first screen explains itself.
The size
About 0.25 dev-days

5

Read the books through books.ts, not Dexie in the page

optional

The problem
The home page runs its own live query on db.books (src/routes/+page.svelte:2,5,9,24). That crosses the architecture's seam "No component calls Dexie directly" (docs/ARCHITECTURE.md:24). It also repeats by hand the soft-delete filter and the sort that listBooks already has (src/lib/books.ts:44-48). BOK-3's close kept this, but only "while that page is the only reader of the books", and M4, M6 and M7 bring more readers.
The change
Add watchBooks() to books.ts, the way shelves.ts has watchShelves(), and have the page use it.
What it wins
One place for the rules on removed books and order, and the seam holds before covers and moves are added.
The size
About 0.25 dev-days

6

Ask before deleting a shelf, and focus the rename field

optional

The problem
Delete removes a shelf at once, with no confirmation or undo (src/routes/+page.svelte:77). Rename opens a field that doesn't take focus (:83), so on a phone the reader has to tap twice. Only empty shelves can be deleted, and the delete is soft, so the harm is small.
The change
Show an "Undo" message after a delete, or ask first, and focus the rename field when it opens.
What it wins
Fewer accidental deletes, and one tap fewer for each rename.
The size
About 0.25 dev-days

7

Let the store's reads use their indexes

optional

The problem
present() is table.filter(...), which scans the whole table (src/lib/store/rows.ts:43-45). So the reads in books.ts and shelves.ts ignore the indexes STO-2 declared on isbn, shelfId, bookId and nextTryAt (src/lib/store/db.ts:53-55). The coming lookup worker needs "the entries due by nextTryAt", which present() can't serve through the index.
The change
Add an indexed form, presentWhere(table, index, value), and use it in books.ts and shelves.ts.
What it wins
One helper that keeps both the soft-delete rule and indexed reads, in place before LKP builds its queue.
The size
About 0.25 dev-days

8

Split the home page before M4 to M8 add to it

optional

The problem
src/routes/+page.svelte is one component holding:
  • the shelf list;
  • each shelf's rename, up, down and delete actions;
  • one shared refusal and renaming state;
  • the add-shelf form;
  • the book list.
The code is at :18-53 and :61-97. Titles, covers, moves and the finished date will each add to the same block for every shelf.
The change
Pull out ShelfSection.svelte and BookItem.svelte into src/lib. The page keeps the list and the add-shelf form.
What it wins
M6 and M7 each change one small component that can be tested alone.
The size
About 0.5 dev-days

9

Keep each shelf's buttons in one place at phone width

optional

The problem
At / at phone width (Pixel 7), the Rename, Up, Down and Delete row stays beside the heading for short names. For "Finished" (whose heading carries a mark) and for longer names, it wraps onto its own line. So the cards end up with different layouts (src/routes/+page.svelte:137-162).
The change
At narrow widths, put the actions on their own row, or fold them into one "⋯" menu per shelf.
What it wins
A steadier, denser phone layout, where Shelf is installed most.

How it was made

Three separate reviews covered sprints 1 and 2, and each read the plan, both sprints' tasks and designs, the open issue and the deferred items. The code review read src/lib, the routes, the service worker and the tests, and ran nothing. The UI review ran the project's Playwright tests (12 passed, desktop and Pixel 7). It then served the build and ran a throwaway script that captured / and /add online and offline at both widths, and cleaned up afterwards. The features review checked each delivered story's Done when against the code and the tests. Item 1 was found by all three on their own, and the line it rests on was checked again. Left out: the "move them to another shelf first" dead end, which M7 covers; the preview footer, which an open issue holds; and smaller repeats, such as the brand colour written in six files.
